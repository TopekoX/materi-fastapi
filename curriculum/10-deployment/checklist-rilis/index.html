    Checklist Rilis¶

    Tujuan pembelajaran¶

    Setelah membaca halaman ini, kamu mampu:

    • Menjelaskan fungsi checklist rilis dan membedakan item yang bisa diperiksa mesin dari yang harus diputuskan manusia.
    • Menelusuri setiap item checklist ke bab yang membahasnya.
    • Menjalankan periksa_rilis.py untuk menyaring kesalahan umum pada sebuah proyek.
    • Membaca hasil LULUS, GAGAL, dan LEWAT, dan memahami batas pemeriksa otomatis.
    • Menyusun checklist sendiri sebelum rilis.

    Prasyarat¶

    • Sudah membaca Server Produksi, Container, Variabel Environment, dan Logging.

    Versi yang diuji

    Skrip dan pengujian di halaman ini dijalankan dengan Python 3.14.7 dan pytest 9.1.1 di Windows (pytest-cov 7.1.0 untuk cakupan). Daftar versi lain ada di Versi yang dipakai di materi ini. Skrip hanya memakai pustaka standar Python. Sistem operasi lain belum diuji.

    Konsep¶

    Checklist rilis adalah daftar pemeriksaan yang dilakukan setiap kali aplikasi akan dirilis ke produksi. Pilot pesawat memakai checklist bukan karena lupa cara terbang, tetapi karena orang yang ahli pun bisa melewatkan satu langkah saat terburu-buru. Hal yang sama berlaku untuk rilis.

    Item checklist terbagi dua jenis:

    Jenis Contoh Cara memeriksa
    Bisa diperiksa mesin .env ada di .gitignore; versi dependensi dikunci Skrip membaca berkas
    Perlu keputusan manusia Apakah /docs boleh terbuka? Siapa yang dihubungi bila gagal? Orang yang bertanggung jawab

    Halaman ini memberi keduanya: daftar lengkap yang ditautkan ke bab asalnya, dan skrip kecil untuk item yang bisa diperiksa mesin.

    Checklist¶

    Setiap item memuat bab tempat ia dibahas. Kolom Otomatis menunjukkan apakah periksa_rilis.py ikut memeriksanya.

    Rahasia dan konfigurasi¶

    Item Bab Otomatis
    Kunci penandatangan token berasal dari environment/secret, bukan dari kode Variabel Environment Sebagian (mendeteksi nilai tertulis di kode)
    Kunci acak dan panjang, bukan kunci contoh Variabel Environment Tidak (diperiksa saat aplikasi mulai)
    .env dan *.db ada di .gitignore Konfigurasi dan Environment Ya
    lingkungan = produksi; mode debug mati Variabel Environment Tidak
    CORS hanya mengizinkan origin frontend yang sah, bukan * CORS Sebagian (mendeteksi allow_origins=["*"] di kode)
    Keputusan tentang /docs dan /openapi.json: terbuka atau ditutup Variabel Environment Tidak

    Aplikasi¶

    Item Bab Otomatis
    Pengujian ada dan lulus; cakupan dilihat Pengujian Endpoint Hanya keberadaannya
    Migrasi basis data ada dan sudah diuji pada salinan data Migrasi Hanya keberadaan alembic.ini
    Basis data produksi bukan SQLite berkas yang tidak dicadangkan Koneksi ke Basis Data Tidak
    Status penting tidak disimpan di memori proses Server Produksi Tidak
    Log tidak memuat rahasia; level bukan DEBUG Logging Tidak

    Container dan server¶

    Item Bab Otomatis
    Versi dependensi dikunci (==) Container Ya
    .dockerignore menutup .env Container Ya
    Container berjalan sebagai pengguna non-root Container Ya
    Tidak ada rahasia di Dockerfile dan Compose Container Ya (heuristik)
    Data ada di volume, bukan di dalam container Container Tidak
    Jumlah worker dipilih dan diukur Server Produksi Tidak
    HTTPS dihentikan di proksi dan header proksi dipercaya dengan benar Server Produksi Tidak

    Operasional¶

    Item Keterangan Otomatis
    Ada cara memeriksa aplikasi hidup (health check) Endpoint sederhana yang bisa dipanggil proksi atau orkestrator Tidak
    Ada cadangan basis data dan cara memulihkannya Dicoba memulihkan, bukan hanya membuat cadangan Tidak
    Ada rencana mundur (rollback) Versi sebelumnya masih tersedia Tidak
    Ada yang dihubungi bila rilis bermasalah Orang dan saluran yang jelas Tidak

    Daftar ini adalah titik awal

    Item operasional di atas adalah praktik umum, bukan sesuatu yang diuji dalam materi ini. Sesuaikan dengan tempat kamu merilis.

    periksa_rilis.py¶

    periksa_rilis.py
    """Pemeriksa checklist rilis (heuristik berbasis teks).

Pemakaian:  python periksa_rilis.py <folder-proyek>

Skrip hanya membaca berkas. Ia tidak menjalankan aplikasi, Docker, atau pengujian,
sehingga LULUS di sini bukan jaminan aman: ini penyaring kesalahan yang paling umum.
"""

import re
import sys
from pathlib import Path
from typing import Callable, NamedTuple

NAMA_RAHASIA = r"(secret|password|kata_sandi|token|api_key)"


class Hasil(NamedTuple):
    nama: str
    status: str  # "LULUS", "GAGAL", atau "LEWAT" (tidak berlaku)
    catatan: str


def berkas_python(folder: Path) -> list[Path]:
    """Semua .py aplikasi, tanpa folder lingkungan virtual dan berkas pengujian."""
    hasil = []
    for p in folder.rglob("*.py"):
        if any(b in {".venv", "venv", "__pycache__", "alembic"} for b in p.parts):
            continue
        if p.name.startswith("test_") or "tests" in p.parts or p.name == "conftest.py":
            continue
        hasil.append(p)
    return hasil


def cari_gitignore(folder: Path) -> Path | None:
    for induk in [folder, *folder.parents][:5]:
        if (induk / ".gitignore").is_file():
            return induk / ".gitignore"
    return None


def baris_aktif(path: Path) -> list[str]:
    return [b.strip() for b in path.read_text(encoding="utf-8").splitlines() if b.strip() and not b.strip().startswith("#")]


def periksa_gitignore(folder: Path) -> Hasil:
    nama = ".env dan *.db diabaikan Git"
    git = cari_gitignore(folder)
    if git is None:
        return Hasil(nama, "GAGAL", "tidak ada .gitignore")
    isi = baris_aktif(git)
    kurang = [x for x in (".env", "*.db") if x not in isi]
    return Hasil(nama, "GAGAL" if kurang else "LULUS", f"belum ada di {git.name}: {', '.join(kurang)}" if kurang else str(git))


def periksa_dockerignore(folder: Path) -> Hasil:
    nama = ".dockerignore menutup .env"
    if not (folder / "Dockerfile").is_file():
        return Hasil(nama, "LEWAT", "tidak ada Dockerfile")
    di = folder / ".dockerignore"
    if not di.is_file():
        return Hasil(nama, "GAGAL", "tidak ada .dockerignore")
    return Hasil(nama, "LULUS" if ".env" in baris_aktif(di) else "GAGAL", ".dockerignore ada")


def periksa_user_bukan_root(folder: Path) -> Hasil:
    nama = "container berjalan sebagai non-root"
    df = folder / "Dockerfile"
    if not df.is_file():
        return Hasil(nama, "LEWAT", "tidak ada Dockerfile")
    pengguna = re.findall(r"^\s*USER\s+(\S+)", df.read_text(encoding="utf-8"), flags=re.M)
    if not pengguna or pengguna[-1] in {"root", "0"}:
        return Hasil(nama, "GAGAL", "tidak ada instruksi USER non-root")
    return Hasil(nama, "LULUS", f"USER {pengguna[-1]}")


def periksa_rahasia_di_dockerfile(folder: Path) -> Hasil:
    nama = "tidak ada rahasia di Dockerfile/Compose"
    ditemukan = []
    for fn in ("Dockerfile", "docker-compose.yml", "compose.yaml"):
        p = folder / fn
        if not p.is_file():
            continue
        for b in p.read_text(encoding="utf-8").splitlines():
            if re.search(NAMA_RAHASIA, b, flags=re.I) and re.search(r"(ENV|ARG|:|=)\s*\S+", b):
                nilai = re.split(r"[:=]", b, maxsplit=1)[-1].strip().strip("\"'")
                if nilai and not nilai.startswith("${") and not b.strip().startswith("#"):
                    ditemukan.append(f"{fn}: {b.strip()}")
    return Hasil(nama, "GAGAL" if ditemukan else "LULUS", "; ".join(ditemukan) if ditemukan else "bersih")


def periksa_requirements_terkunci(folder: Path) -> Hasil:
    nama = "versi dependensi dikunci (==)"
    req = folder / "requirements.txt"
    if not req.is_file():
        return Hasil(nama, "GAGAL", "tidak ada requirements.txt di folder ini")
    longgar = [b for b in baris_aktif(req) if "==" not in b]
    return Hasil(nama, "GAGAL" if longgar else "LULUS", ", ".join(longgar) if longgar else f"{len(baris_aktif(req))} paket")


def periksa_cors(folder: Path) -> Hasil:
    nama = "CORS tidak memakai '*' di kode"
    cacat = [
        p.name
        for p in berkas_python(folder)
        if re.search(r"allow_origins\s*=\s*\[\s*[\"']\*[\"']\s*\]", p.read_text(encoding="utf-8"))
    ]
    return Hasil(nama, "GAGAL" if cacat else "LULUS", ", ".join(cacat) if cacat else "tidak ditemukan")


def periksa_rahasia_di_kode(folder: Path) -> Hasil:
    nama = "tidak ada rahasia tertulis di kode"
    pola = re.compile(rf"(secret|password|kata_sandi|api_key)\w*\s*(:\s*\w+\s*)?=\s*[\"'][^\"']{{6,}}[\"']", re.I)
    ditemukan = [
        f"{p.name}:{no}"
        for p in berkas_python(folder)
        for no, b in enumerate(p.read_text(encoding="utf-8").splitlines(), 1)
        if pola.search(b)
    ]
    return Hasil(nama, "GAGAL" if ditemukan else "LULUS", ", ".join(ditemukan) if ditemukan else "tidak ditemukan")


def periksa_ada_pengujian(folder: Path) -> Hasil:
    nama = "ada pengujian"
    ada = any(folder.rglob("test_*.py")) or (folder / "tests").is_dir()
    return Hasil(nama, "LULUS" if ada else "GAGAL", "berkas test_*.py ditemukan" if ada else "tidak ada")


def periksa_migrasi(folder: Path) -> Hasil:
    nama = "ada konfigurasi migrasi (Alembic)"
    ada = (folder / "alembic.ini").is_file()
    return Hasil(nama, "LULUS" if ada else "GAGAL", "alembic.ini ada" if ada else "tidak ada alembic.ini")


PEMERIKSA: list[Callable[[Path], Hasil]] = [
    periksa_gitignore,
    periksa_dockerignore,
    periksa_user_bukan_root,
    periksa_rahasia_di_dockerfile,
    periksa_requirements_terkunci,
    periksa_cors,
    periksa_rahasia_di_kode,
    periksa_ada_pengujian,
    periksa_migrasi,
]


def jalankan(folder: Path) -> list[Hasil]:
    return [periksa(folder) for periksa in PEMERIKSA]


def main(argv: list[str]) -> int:
    if len(argv) != 2:
        print("Pemakaian: python periksa_rilis.py <folder-proyek>")
        return 2
    folder = Path(argv[1]).resolve()
    if not folder.is_dir():
        print(f"Folder tidak ditemukan: {folder}")
        return 2
    hasil = jalankan(folder)
    for h in hasil:
        print(f"[{h.status:5}] {h.nama} - {h.catatan}")
    gagal = sum(h.status == "GAGAL" for h in hasil)
    print(f"\n{gagal} gagal dari {len(hasil)} pemeriksaan")
    return 1 if gagal else 0


if __name__ == "__main__":
    sys.exit(main(sys.argv))

    Penjelasan kode¶

    • Hasil adalah tupel bernama berisi nama pemeriksaan, status (LULUS, GAGAL, atau LEWAT), dan catatan singkat. LEWAT berarti pemeriksaan tidak berlaku, misalnya tidak ada Dockerfile sehingga .dockerignore tidak perlu diperiksa.
    • berkas_python mengumpulkan berkas .py aplikasi dengan mengabaikan lingkungan virtual, alembic, dan berkas pengujian. Berkas pengujian dikecualikan karena wajar memuat kata sandi palsu.
    • cari_gitignore naik hingga lima tingkat folder untuk menemukan .gitignore, karena contoh berada di dalam repositori yang .gitignore-nya ada di akar.
    • baris_aktif membaca baris yang bukan kosong dan bukan komentar, supaya # .env tidak dianggap sebagai aturan.
    • Fungsi periksa_* masing-masing memeriksa satu item dan mengembalikan satu Hasil. Pemeriksaan rahasia memakai ekspresi reguler yang mencari nama seperti secret, password, kata_sandi, atau api_key yang diberi nilai teks sepanjang minimal enam karakter. Nilai berbentuk ${...} di Compose dianggap rujukan variabel, bukan rahasia.
    • PEMERIKSA adalah daftar semua pemeriksaan; menambah item berarti menulis fungsi dan menambahkannya ke daftar ini.
    • main mencetak satu baris per pemeriksaan dan mengembalikan kode keluar 1 bila ada yang gagal, 0 bila tidak, dan 2 bila argumen salah. Kode keluar ini memungkinkan skrip dipakai di CI untuk menghentikan rilis.

    Ini penyaring, bukan jaminan

    Skrip hanya membaca teks. Ia tidak menjalankan aplikasi, Docker, atau pengujian. LULUS berarti pola buruk yang dicari tidak ditemukan, bukan berarti proyek aman. Rahasia dengan nama tak terduga, atau konfigurasi yang salah tetapi tertulis rapi, tidak akan terdeteksi.

    Menjalankan¶

    Dari folder examples/fastapi/10-deployment/checklist-rilis:

    python periksa_rilis.py ..\..\proyek\tahap-5

    Keluaran nyata (jalur .gitignore dipersingkat):

    [LULUS] .env dan *.db diabaikan Git - .gitignore
[LEWAT] .dockerignore menutup .env - tidak ada Dockerfile
[LEWAT] container berjalan sebagai non-root - tidak ada Dockerfile
[LULUS] tidak ada rahasia di Dockerfile/Compose - bersih
[GAGAL] versi dependensi dikunci (==) - tidak ada requirements.txt di folder ini
[LULUS] CORS tidak memakai '*' di kode - tidak ditemukan
[LULUS] tidak ada rahasia tertulis di kode - tidak ditemukan
[LULUS] ada pengujian - berkas test_*.py ditemukan
[LULUS] ada konfigurasi migrasi (Alembic) - alembic.ini ada

1 gagal dari 9 pemeriksaan

    Kode keluarnya 1. Artinya Proyek Tahap 5 belum siap dirilis: ia belum punya requirements.txt yang dikunci, dan belum punya Dockerfile. Itulah yang dikerjakan di Container dan Proyek Praktik Tahap 6.

    Folder contoh Container juga diperiksa:

    python periksa_rilis.py ..\container

    Hasilnya: .gitignore, .dockerignore, USER aplikasi, rahasia di Dockerfile/Compose, dan requirements.txt (6 paket) semuanya LULUS; ada pengujian dan ada konfigurasi migrasi GAGAL (2 gagal dari 9 pemeriksaan). Itu benar, karena folder tersebut hanya berisi berkas container, bukan aplikasinya.

    Pelajaran dari percobaan pertama¶

    Pada percobaan pertama, pemeriksa rahasia menandai Tahap 5 GAGAL pada auth.py baris 45. Penyebabnya ternyata Token(..., token_type="bearer"): kata token cocok dengan pola, padahal "bearer" bukan rahasia (hasil positif palsu). Kata token dikeluarkan dari pola pemeriksaan kode dan ditambahkan pengujian test_token_type_bukan_rahasia. Pemeriksa heuristik akan selalu punya positif palsu dan negatif palsu; jangan percaya buta pada hasilnya, baik LULUS maupun GAGAL.

    Pengujian¶

    python -m pytest -q

    Hasil nyata:

    16 passed in 0.23s

    Cakupan cabang (--cov=periksa_rilis --cov-branch) bernilai 92%. Baris yang belum tercakup: pelewatan folder lingkungan virtual, kasus tanpa .gitignore, kasus tanpa requirements.txt, dan blok if __name__ == "__main__".

    Pengujian membuat proyek palsu di folder sementara (tmp_path), memastikan proyek yang baik LULUS semua, lalu merusaknya satu per satu dan memastikan pemeriksaan yang sesuai GAGAL. Pengujian juga memeriksa kasus LEWAT dan kode keluar main.

    Kesalahan umum¶

    Kesalahan Penjelasan
    Menjalankan checklist hanya sekali di awal Jalankan setiap rilis; konfigurasi berubah seiring waktu.
    Mengandalkan skrip otomatis saja Item penting seperti keputusan /docs dan cadangan butuh manusia.
    Menganggap LULUS berarti aman Skrip mencari pola yang dikenal saja.
    Mengabaikan LEWAT Pastikan memang tidak berlaku, bukan karena berkas salah tempat.
    Menambah item tanpa pernah mengujinya Item otomatis harus punya pengujian yang membuktikan ia bisa gagal.
    Checklist tidak diperbarui setelah insiden Setiap insiden yang bisa dicegah layak menjadi item baru.

    Latihan¶

    1. Dasar. Sebutkan dua item yang bisa diperiksa mesin dan dua yang harus diputuskan manusia.
    2. Prediksi. Apa kode keluar periksa_rilis.py bila satu pemeriksaan GAGAL, dan bila semuanya LULUS atau LEWAT?
    3. Praktik. Tambahkan pemeriksaan periksa_healthcheck yang LULUS bila ada berkas .py aplikasi yang memuat "/health". Tambahkan juga ke PEMERIKSA dan tulis dua pengujian (ada dan tidak ada).
    4. Analisis. Beri satu contoh rahasia yang lolos dari periksa_rahasia_di_kode.
    Kunci jawaban
    1. Mesin: .env di .gitignore, versi dependensi dikunci. Manusia: apakah /docs terbuka, siapa yang dihubungi bila rilis bermasalah.
    2. 1 bila ada yang GAGAL; 0 bila semuanya LULUS atau LEWAT (teruji pada test_main_kode_keluar).
    3. Penerapan pola yang sama dengan fungsi lain; tidak dijalankan di halaman ini. Kerangka: baca berkas_python(folder) dan cek '"/health"' in teks, kembalikan Hasil("ada health check", "LULUS" atau "GAGAL", ...).
    4. Misalnya kunci = "abc" (nama tidak ada di daftar), atau nilai yang dirakit dari dua bagian string. Nama token juga sengaja tidak diperiksa (lihat bagian pelajaran di atas).

    Ringkasan¶

    • Checklist rilis mencegah langkah yang terlewat; sebagian bisa diperiksa mesin, sebagian harus diputuskan manusia.
    • Setiap item ditautkan ke bab asalnya, supaya alasan di baliknya mudah dibuka kembali.
    • periksa_rilis.py memeriksa sembilan hal lewat pembacaan berkas dan mengembalikan kode keluar yang bisa dipakai di CI.
    • Hasil heuristik bisa salah (positif dan negatif palsu), jadi LULUS bukan jaminan.
    • Pada Tahap 5, pemeriksa menemukan 1 kegagalan nyata: belum ada dependensi yang dikunci.
