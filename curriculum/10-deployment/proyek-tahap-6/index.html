    Proyek Praktik Tahap 6¶

    Tujuan pembelajaran¶

    Setelah mengerjakan halaman ini, kamu mampu:

    • Menyiapkan aplikasi yang sudah teruji (Tahap 5) agar siap dijalankan di produksi.
    • Menambahkan pembeda lingkungan dan aturan produksi pada konfigurasi.
    • Menambahkan logging terstruktur dengan request ID ke aplikasi nyata.
    • Membuat endpoint liveness (/kesehatan) dan readiness (/siap), dan membedakan keduanya.
    • Menutup dokumentasi interaktif di produksi.
    • Mengemas aplikasi dengan Dockerfile dan Compose, dan memahami bagian mana yang belum terverifikasi.
    • Menilai kesiapan rilis dengan periksa_rilis.py.

    Prasyarat¶

    • Sudah mengerjakan Proyek Praktik Tahap 5. Tahap 6 memakai kode dan seluruh pengujiannya.
    • Sudah membaca halaman Modul 10 sebelumnya: Server Produksi, Container, Variabel Environment, Logging, dan Checklist Rilis.

    Versi yang diuji

    Kode dan output di halaman ini dijalankan dengan Python 3.14.7, FastAPI 0.162.0, SQLModel 0.0.48, Alembic 1.20.1, pydantic-settings 2.16.1, pytest 9.1.1, dan pytest-cov 7.1.0 di Windows. Daftar versi lain ada di Versi yang dipakai di materi ini. Versi lain dan sistem operasi lain belum diuji.

    Docker tidak dijalankan di tahap ini

    Sama seperti halaman Container: daemon Docker tidak aktif di mesin penulis, sehingga docker build, docker run, dan docker compose tidak pernah dijalankan. Yang diuji adalah langkah-langkah di dalam Dockerfile yang diemulasikan di luar Docker (lihat Menjalankan seperti di container). Bacalah perintah Docker di halaman ini sebagai rancangan yang belum terverifikasi.

    app/config.py¶

    app/config.py
    from functools import lru_cache
from typing import Literal

from pydantic import Field, SecretStr, model_validator
from pydantic_settings import BaseSettings, SettingsConfigDict

# Awalan kunci yang biasa dipakai pada contoh; ditolak di produksi
KUNCI_CONTOH = "ganti-dengan-kunci-acak"


class Settings(BaseSettings):
    # Dibaca dari variabel environment berawalan TUGASKU_ atau dari berkas .env.
    # extra="ignore": entri lain di .env (misalnya milik Docker Compose) tidak menggagalkan aplikasi.
    model_config = SettingsConfigDict(env_prefix="TUGASKU_", env_file=".env", extra="ignore")

    nama_aplikasi: str = "TugasKu API"
    lingkungan: Literal["pengembangan", "uji", "produksi"] = "pengembangan"
    database_url: str = "sqlite:///database.db"
    algoritma: str = "HS256"
    detik_akses: int = Field(default=1800, ge=60)
    origin_diizinkan: list[str] = ["http://localhost:3000"]
    secret_key: SecretStr = Field(min_length=32)  # wajib diisi
    log_level: Literal["DEBUG", "INFO", "WARNING", "ERROR", "CRITICAL"] = "INFO"
    log_format: Literal["teks", "json"] = "teks"

    @model_validator(mode="after")
    def periksa_aturan_produksi(self) -> "Settings":
        """Tolak konfigurasi berbahaya saat aplikasi mulai, bukan setelah pengguna menemukannya."""
        if self.lingkungan == "produksi":
            masalah = []
            if "*" in self.origin_diizinkan:
                masalah.append("origin_diizinkan tidak boleh berisi '*'")
            if self.secret_key.get_secret_value().startswith(KUNCI_CONTOH):
                masalah.append("secret_key masih kunci contoh")
            if masalah:
                raise ValueError("Konfigurasi produksi tidak aman: " + "; ".join(masalah))
        return self


@lru_cache
def get_settings() -> Settings:
    return Settings()

    app/main.py¶

    app/main.py
    import logging
import time
import uuid

from fastapi import FastAPI, HTTPException, Request
from fastapi.middleware.cors import CORSMiddleware
from sqlmodel import text

from .config import get_settings
from .database import SessionDep
from .errors import pasang_penangan_error
from .pengaturan_log import atur_logging, request_id_var
from .routers import auth, kategori, tugas

settings = get_settings()
atur_logging(level=settings.log_level, format_log=settings.log_format)
log = logging.getLogger("tugasku.aplikasi")

# Di produksi dokumentasi interaktif ditutup (keputusan, bukan keharusan; lihat Checklist Rilis)
produksi = settings.lingkungan == "produksi"
app = FastAPI(
    title=settings.nama_aplikasi,
    description="TugasKu API (siap deploy)",
    docs_url=None if produksi else "/docs",
    redoc_url=None if produksi else "/redoc",
    openapi_url=None if produksi else "/openapi.json",
)

app.add_middleware(
    CORSMiddleware,
    allow_origins=settings.origin_diizinkan,
    allow_methods=["GET", "POST", "PUT", "PATCH", "DELETE"],
    allow_headers=["Authorization", "Content-Type"],
)


@app.middleware("http")
async def catat_request(request: Request, call_next):
    request_id = request.headers.get("x-request-id") or uuid.uuid4().hex[:8]
    token = request_id_var.set(request_id)
    mulai = time.perf_counter()
    try:
        response = await call_next(request)
        durasi_ms = (time.perf_counter() - mulai) * 1000
        log.info("%s %s -> %s (%.1f ms)", request.method, request.url.path, response.status_code, durasi_ms)
        response.headers["X-Request-ID"] = request_id
        return response
    except Exception:
        log.exception("request gagal: %s %s", request.method, request.url.path)
        raise
    finally:
        request_id_var.reset(token)


pasang_penangan_error(app)


@app.get("/kesehatan", tags=["operasional"])
def kesehatan():
    """Liveness: proses hidup dan bisa menjawab. Tidak menyentuh basis data."""
    return {"status": "ok"}


@app.get("/siap", tags=["operasional"])
def siap(session: SessionDep):
    """Readiness: aplikasi bisa bekerja, termasuk menjangkau basis data."""
    try:
        session.exec(text("SELECT 1"))
    except Exception:
        log.exception("pemeriksaan kesiapan gagal")
        raise HTTPException(status_code=503, detail="Basis data belum siap")
    return {"status": "siap"}


app.include_router(auth.router)
app.include_router(kategori.router)
app.include_router(tugas.router)

    Dockerfile
    # Dockerfile untuk TugasKU API (versi siap deploy, proyek tahap 6).
# Letakkan di folder yang sama dengan requirements.txt, alembic.ini, alembic/, dan app/.
#
# CATATAN: Dockerfile ini BELUM dibangun atau dijalankan saat materi ditulis,
# karena daemon Docker tidak aktif pada mesin penulis. Lihat penjelasan di halaman Container.

FROM python:3.14

WORKDIR /code

# Salin daftar dependensi lebih dulu. Lapisan ini hanya dibangun ulang bila requirements.txt berubah.
COPY ./requirements.txt /code/requirements.txt
RUN pip install --no-cache-dir --upgrade -r /code/requirements.txt

# Salin kode aplikasi dan migrasi. Bagian ini paling sering berubah, jadi ditaruh paling akhir.
COPY ./app /code/app
COPY ./alembic.ini /code/alembic.ini
COPY ./alembic /code/alembic

# Jalankan sebagai pengguna biasa, bukan root
RUN useradd --create-home --uid 1000 aplikasi \
    && mkdir /data \
    && chown aplikasi:aplikasi /data
USER aplikasi

# Basis data SQLite disimpan di /data, yang dipasang sebagai volume agar data tidak hilang
ENV TUGASKU_DATABASE_URL=sqlite:////data/database.db
VOLUME ["/data"]

# Agar perintah alembic yang dijalankan dari folder lain (/data) tetap bisa mengimpor paket "app"
ENV PYTHONPATH=/code

EXPOSE 8000

# Bentuk exec (dengan tanda kurung siku): memungkinkan penghentian baik-baik dan menjalankan lifespan.
# Satu proses per container; replikasi diserahkan ke pengelola container.
CMD ["fastapi", "run", "app/main.py", "--port", "8000", "--proxy-headers"]

    Penjelasan kode¶

    config.py¶

    • lingkungan dibatasi Literal pada tiga nilai; nilai lain ditolak saat aplikasi mulai.
    • log_level dan log_format juga Literal, sehingga TUGASKU_LOG_LEVEL=CERewET ditolak (teruji).
    • extra="ignore" membuat entri lain di .env (misalnya milik Compose) tidak menggagalkan aplikasi. Risikonya: salah ketik nama variabel tidak ketahuan. Lihat Variabel Environment.
    • periksa_aturan_produksi hanya berlaku bila lingkungan == "produksi". Ia menolak origin * dan kunci yang masih berawalan KUNCI_CONTOH. Aturan mode debug dari halaman Variabel Environment tidak dipakai di sini karena aplikasi ini tidak punya pengaturan debug.

    main.py¶

    • atur_logging(...) dipanggil sekali saat modul diimpor, dengan level dan format dari konfigurasi.
    • Dokumentasi (docs_url, redoc_url, openapi_url) bernilai None di produksi sehingga /docs, /redoc, dan /openapi.json menjawab 404. Menutup dokumentasi adalah keputusan, bukan keharusan; pilihlah sesuai kebutuhan timmu.
    • Middleware catat_request sama dengan di halaman Logging: menentukan request ID, mencatat satu baris per request, dan menaruh ID di header X-Request-ID.
    • /kesehatan menjawab selama proses hidup dan tidak menyentuh basis data. Ini liveness: "prosesnya hidup?".
    • /siap menjalankan SELECT 1 lewat sesi basis data. Bila gagal, ia mencatat galat dan menjawab 503. Ini readiness: "siap melayani pekerjaan?". Pembeda keduanya penting: bila basis data mati, memulai ulang proses tidak menolong, jadi /kesehatan tetap 200 tetapi /siap menjadi 503.
    • Kedua endpoint ini tidak memerlukan login, supaya bisa dipanggil proksi atau orkestrator.

    Dockerfile, Compose, dan .env.contoh¶

    Sama dengan yang dijelaskan di halaman Container: berkas dependensi disalin lebih dulu agar lapisan pip install bisa dipakai ulang, aplikasi berjalan sebagai pengguna aplikasi (bukan root), basis data SQLite ada di /data yang dipasang sebagai volume, dan rahasia datang dari environment saat container dijalankan. .env.contoh hanya berisi nilai tiruan; salin menjadi .env untuk dipakai Compose.

    Pengujian¶

    Hasil nyata:

    67 passed in 5.20s

    Rinciannya: 54 pengujian dari Tahap 5 ditambah 13 pengujian dari test_deploy.py. Cakupan cabang untuk paket app bernilai 98% (359 pernyataan, 6 belum tercakup): 4 di pengaturan_log.py (kelas FormatJson, yang diuji di halaman Logging, bukan di sini) dan 2 di database.py (fungsi get_session asli, yang selalu diganti saat pengujian).

    Merusak aplikasi dengan sengaja¶

    Seperti di Tahap 5, mutu pengujian diuji dengan merusak aplikasi:

    Kerusakan Hasil
    Aturan produksi dimatikan (if False:) 2 pengujian gagal
    Dokumentasi selalu terbuka di produksi 1 pengujian gagal
    /siap tidak lagi menyentuh basis data 1 pengujian gagal

    Kerusakan ketiga awalnya lolos tanpa terdeteksi: pengujian /siap hanya memeriksa kasus basis data sehat, sehingga tidak bisa membedakan /siap yang benar dari yang pura-pura. Itu dibenahi dengan menambah test_siap_gagal_503_bila_basis_data_bermasalah (sesi yang sengaja rusak), sekaligus mengubah /siap agar menjawab 503 dan tidak 500. Setelah itu kerusakan ketiga tertangkap.

    Menjalankan seperti di container¶

    Langkah di Dockerfile diemulasikan tanpa Docker: salin app, alembic, dan alembic.ini ke folder code; siapkan folder data kosong; jalankan migrasi dari folder data dengan PYTHONPATH menunjuk ke code; jalankan server dari code dengan variabel environment produksi (lingkungan=produksi, log JSON, origin https://tugasku.contoh, kunci acak 64 karakter).

    Migrasi membuat database.db di folder data. Lalu:

    Permintaan Hasil
    GET /kesehatan 200
    GET /siap 200, {"status":"siap"}
    GET /docs, GET /openapi.json 404
    POST /daftar (pengguna budi) 201
    Server dimulai ulang, POST /daftar lagi 409 NAMA_PENGGUNA_SUDAH_ADA (data bertahan)

    Latihan¶

    1. Dasar. Apa beda /kesehatan dan /siap? Mana yang berubah menjadi 503 saat basis data tidak terjangkau?
    2. Prediksi. Aplikasi dijalankan dengan TUGASKU_LINGKUNGAN=produksi dan TUGASKU_SECRET_KEY=ganti-dengan-kunci-acak-minimal-32-karakter. Apa yang terjadi?
    3. Praktik. Tambahkan aturan produksi: database_url tidak boleh mengandung sqlite. Tulis pengujian untuk aturan itu di test_deploy.py, lalu pastikan pengujian lama masih lulus.
    4. Analisis. Mengapa /siap tidak boleh meminta login?
    Kunci jawaban
    1. /kesehatan menandakan proses hidup dan tidak menyentuh basis data; /siap memeriksa basis data. Yang menjadi 503 adalah /siap.
    2. Aplikasi menolak mulai: kunci itu berawalan KUNCI_CONTOH, sehingga periksa_aturan_produksi melempar ValidationError "secret_key masih kunci contoh" (teruji pada test_produksi_menolak_konfigurasi_berbahaya).
    3. Tambahkan if "sqlite" in self.database_url: masalah.append("database_url tidak boleh SQLite di produksi") di blok produksi. Perhatian: nilai bawaan database_url memakai SQLite, jadi pengujian produksi yang sudah ada perlu memberikan database_url non-SQLite, dan emulasi container di halaman ini (yang memakai SQLite) tidak akan lagi bisa mulai dalam mode produksi. Ini penerapan pola dan tidak dijalankan di halaman ini.
    4. Proksi dan orkestrator memanggilnya tanpa kredensial; bila butuh login, mereka akan selalu menerima 401 dan menganggap aplikasi tidak siap.
